## Q01 · RAG 是什么 / 为什么需要

### RAG 解决的核心问题

模型在运行时**需要知道什么**。

RAG 做法：先从外部文档库**检索**，再带着检索到的证据**生成**答案。

适合：**FAQ、企业知识库、规章制度、产品文档、法律/医学资料问答**这类"答案要以文档为准"的任务。

### 标准流水线

```
用户 Query
   ↓
[1] Query 理解 / 改写
   ↓
[2] 检索相关文档（多路召回）
   ↓
[3] 重排序（Reranking）
   ↓
[4] 拼接 Prompt（context + query）
   ↓
[5] LLM 生成答案
```

### 追问

- **Q：RAG 比直接微调好在哪？**
  A：
  1. **可更新**：换文档库就能换知识，不用重训
  2. **可追溯**：能告诉你证据在哪
  3. **省成本**：不需要为每个领域训一个模型
  4. **隐私**：知识库可本地部署

## Q02 · 索引构建

### 整体流程

```
原始文档 → 解析(PDF/HTML/...) → 清洗 → 分块(Chunking) → 向量化(Embedding) → 存入向量数据库
```

### 文本切分（Chunking）

文档通常太长，不能整篇直接检索，要切成小块。

| 策略 | 描述 | 适用 |
|---|---|---|
| **固定大小** | 按 token 数切分 | 简单文本 |
| **句子级** | 按句号切 | 精确检索 |
| **段落级** | 按段落切 | 保上下文 |
| **递归分割** | 按分隔符递归切 | 通用（**推荐**） |
| **语义分割** | 按语义相似度切 | 高质量 |

**Chunk 大小建议**：

- 通常 **256-1024 tokens**
- 加 **10-20% overlap**（避免语义被切断）
- 根据下游任务调整

这些数字只是起点。Chunk 设计本质是三个量的折中：块太小，相关事实可能被切散且缺少回答上下文；块太大，embedding 被多个主题平均、召回精度下降，还会浪费生成上下文。Overlap 能缓解跨边界信息丢失，但会制造近重复结果，因此检索后通常还要去重或按 parent document 合并。最终应同时看 Recall@K、送入生成器的有效 token 比例和答案正确率，而不是单独调 chunk size。

### 向量化（Embedding）

把每个 chunk 编码成向量，**相似语义在向量空间中接近**。

检索时必须和模型训练口径一致：有的模型要求 query/document 使用不同前缀；若用 cosine similarity，通常先做 L2 归一化，此时 cosine 等价于归一化向量的点积。未归一化直接用 dot product 会把向量范数也当成相关性信号，这可能是模型设计的一部分，也可能造成高范数文档无故占优。

#### 常用 Embedding 模型

| 模型 | 维度 | 特点 |
|---|---|---|
| OpenAI text-embedding-3-large | 3072 | 商业 API，多语言 |
| **BGE-M3** | 1024 | 多语言、多粒度，开源 |
| E5-Mistral-7B-Instruct | 4096 | 指令增强 |
| GTE-Qwen2 | 1024 | 中英双语优秀 |

### 向量数据库

存储 + 索引 embedding，支持快速近邻搜索：

- **FAISS**：Meta 开源，快但要自己加持久化
- **Milvus / Qdrant / Weaviate**：开源向量数据库
- **Chroma**：轻量，本地用
- **Pinecone**：商业 SaaS

### 追问

- **Q：Chunk 越小越好吗？**
  A：不一定。太小丢失上下文，太大稀释语义。需要根据任务实验，常见 512 tokens 起步。

## Q03 · 查询改写

完整的 RAG 在线流程不是直接检索，更像：

$$
\text{Query} \to \text{Query 改写} \to \text{召回} \to \text{重排} \to \text{上下文构建}
$$

### 1) Query 规范化

清洗原始问题：

- 统一大小写
- 视检索器决定是否去停用词；对 BM25 可能有益，但对神经 embedding，删除否定词、时间词等可能改变语义
- 标准化术语
- 缩写展开
- 拼写纠正

### 2) Query 改写

把自然语言改写为更适合检索的 query：

- 关键词更明确
- 语义更完整
- 专业术语更规范

### 3) Query 扩展

太短的 query 扩展出**相关词、同义词、上下位词**。

### 4) Query 拆解

复杂问题不能一次检索完成，**拆解成多个子问题**。
例：「2024 年中国 GDP 和美国 GDP 分别是多少？」→ 拆成 2 个子问题。

### 高级方案

- **HyDE**（Hypothetical Document Embeddings）：让 LLM 先**假设性地写一个回答**，再用这个回答去做向量检索（让检索目标语义更接近文档语义）
- **Multi-Query**：让 LLM 改写出多个等价 query，并行检索后合并

## Q04 · 召回策略

### 三大检索方式

| 方法 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **向量检索** | 语义相似度 | 理解语义 | 精确匹配差 |
| **关键词（BM25）** | 词频统计 | 精确匹配好 | 不理解语义 |
| **混合检索** | **两者结合** | **互补** | 需要融合 |

BM25 不只是“看词频”：它对 query term 的文档频率做 IDF 加权，对单文档内词频做饱和，并用文档长度归一化。词出现 10 次不会比出现 1 次线性重要，这能抑制长文档和关键词堆砌；但同义表达仍是它的短板，所以常与向量召回互补。

### 混合检索的融合方式

最常用 **RRF（Reciprocal Rank Fusion）**：

$$
\text{score}(d) = \sum_i \frac{1}{k + \text{rank}_i(d)}
$$

RRF 只使用各路排名，不直接比较不可校准的 BM25 分数和向量相似度。常数 $k$ 控制头部排名差异的敏感度：$k$ 小时更偏爱每路前几名，$k$ 大时排名差距被压平。它稳健但会丢弃原始 score 的置信度；若分数可校准，也可以学习融合权重。

### 多路召回

从多个视角召回，最后合并：

- 原始 query
- 改写 query
- 扩展 query
- 子问题 query

### 召回数量

一般初召回 **Top-20/50/100**，后续 rerank 选 **Top-3/5**。

## Q05 · 重排序

### 为什么需要 Reranking？

向量检索本质是**看"谁最像"**，而不是**"谁最能回答"**。
重排序用 **Cross-Encoder**：query 和 doc 一起编码，精度更高。

### 双塔 vs 单塔

| | Bi-Encoder（双塔） | Cross-Encoder（单塔） |
|---|---|---|
| 编码 | query 和 doc 分别编码 | 一起编码 |
| 速度 | 快（向量可预存） | 慢（每对都要算） |
| 精度 | 中 | **高** |
| 用途 | 一阶段召回 | 二阶段精排 |

### 常用 Reranker

- **BGE-Reranker-v2**（国内首选，开源）
- **Cohere Reranker**（商业）
- **Cross-Encoder/ms-marco**（学术基线）

### 追问

- **Q：为什么不直接用 cross-encoder 跑全库检索？**
  A：太慢。cross-encoder 每次要重新编码（query, doc）对，全库 N 万条要算 N 万次 forward。

## Q06 · RAG 评测指标

| 维度 | 指标 | 衡量 |
|---|---|---|
| **检索质量** | Recall@K, MRR, NDCG | 检索准确性 |
| **生成忠实度** | Faithfulness | 是否基于检索内容 |
| **答案相关性** | Answer Relevancy | 回答是否切题 |
| **上下文精确度** | Context Precision | 检索结果相关性 |

### 关键指标解释

- **Recall@K**：Top-K 命中的相关文档数 / 全部已标注相关文档数
- **Precision@K**：Top-K 命中的相关文档数 / K（假设返回恰好 K 条）
- **Hit@K**：Top-K 是否至少命中一条相关文档，单 query 为 0 或 1
- **MRR**（Mean Reciprocal Rank）：第一个相关文档排名的倒数均值
- **NDCG**：考虑排序位置的加权指标
- **Faithfulness**：答案中的事实是否都有 context 支撑（防幻觉）

例：某 query 共有 5 条相关文档，Top-3 命中 2 条，则 Recall@3=2/5，Precision@3=2/3，Hit@3=1。只有每个 query 恰好一条相关文档时，Recall@K 才与 Hit@K 相同。多 query 的宏平均先计算各 query 指标再平均；微平均先累计命中数和分母，二者权重不同。没有标注相关文档的 query 要明确排除或约定分数，不能无说明地除以零；标注不完整时指标也会低估真实相关性。

Recall@K 与 Context Precision 必须一起看：扩大 K 通常提高召回，却可能把更多噪声塞给生成器。端到端失败还应拆成“证据没召回”“召回了但没排前”“上下文中有证据但模型没利用”“模型生成了无证据结论”四类，否则只看最终正确率无法定位组件。

### 评测框架

- **RAGAS**：自动化 RAG 评测，支持上述四大指标
- **TruLens**：可视化 RAG 调试

## Q07 · 高级 RAG

### Agentic RAG

让 **Agent 决定何时检索、检索什么、如何使用结果**：

```
用户查询
  → Agent 判断：需要检索吗？
    → 是：制定检索策略 → 检索 → 判断结果是否充分
      → 不充分：改写查询重新检索
      → 充分：生成回答
    → 否：直接回答
```

### Graph RAG

利用**知识图谱**增强检索：

- 实体识别 → 构建 KG → 图检索 + 向量检索
- 适合**多跳推理和关系型查询**

例：「张三的同事的导师是谁？」需要跨多个三元组才能回答。

### Self-RAG

让模型自己学会**何时引用、何时直接答**，并对自己的输出做反思。

## Q08 · RAG vs 长上下文 vs 微调

| 维度 | RAG | 长上下文 | 微调 |
|---|---|---|---|
| **更新成本** | 低（换库） | 中（重传） | 高（重训） |
| **可追溯** | 有引用 | 有原文 | 参数中知识难定位 |
| **训练成本** | 可为 0；也可训练 embedding/reranker | 通常无需训练 | 通常较高 |
| **推理成本** | 中 | 高（KV Cache 大） | 低 |
| **新知识更新** | 快，更新索引即可 | 快，重新提供上下文 | 慢，需继续训练且难精确删除 |
| **风格定制** | 弱 | 弱 | 强 |
| **指令遵循** | 不直接解决 | 中 | 强 |

**通常组合用**：

- 风格 + 指令 → SFT
- 知识 → RAG
- 短期上下文 → 长上下文窗口

### 追问

- **Q：长上下文模型出了，RAG 是不是被淘汰了？**
  A：不会。RAG 在以下场景仍优：
  1. 知识库远超模型上下文（百万文档）
  2. 需要**可追溯证据**（医疗、法律）
  3. **权限与治理**：可在检索层做文档级 ACL、审计和删除；但被召回的私有内容仍会进入生成模型上下文，若调用外部 API 仍需单独评估数据边界
  4. **成本**：长上下文每次调用都很贵
